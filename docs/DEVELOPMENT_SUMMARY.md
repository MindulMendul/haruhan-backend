# 개발 요약

이 문서는 `claude/fastapi-architecture-improvements-pax3xs` 브랜치(PR #5)에서
자동 개발 루프(Claude Code Remote Routine)가 209라운드에 걸쳐 진행한 작업을
사람이 훑어보기 좋게 정리한 요약입니다. 원본 기록인 `docs/ROADMAP.md`는
라운드마다 원인 분석·재현 방법·검증 절차까지 담은 8000줄이 넘는 개발 로그라
전체를 읽기엔 부담스럽습니다 — 이 문서는 그 233개 항목을 주제별로 묶어
"무엇이 왜 바뀌었는지"만 상위 레벨로 추립니다. API 엔드포인트 하나하나의
스펙은 `docs/FRONTEND_INTEGRATION.md`를 참고하세요.

루프는 매 사이클마다 로드맵의 다음 미완료 항목을 하나 골라 구현·테스트·커밋까지
마치고 이 브랜치에 push하는 방식으로 동작했습니다. 백로그가 바닥나면 코드베이스를
다시 훑어 새 개선 항목을 스스로 찾아 백로그에 추가한 뒤 그 자리에서 구현까지
마치는 식으로 209라운드가 이어졌습니다 — PR 머지는 사람이 직접 합니다.

## 핵심 기능

haruhan-backend는 학습/면접 준비를 돕는 4개 핵심 기능을 제공하는 FastAPI
백엔드입니다. **학습챗**은 세션 기반으로 AI와 대화하며 학습 내용을 정리하고,
**퀴즈**는 학습챗 세션이나 직접 붙여넣은 텍스트를 소스로 AI가 객관식 문제를
생성해 채점·재도전·오답노트까지 지원합니다. **면접연습**은 AI가 질문을 던지고
사용자가 답하면 피드백과 다음 질문을 이어가는 턴 기반 세션이고, **면접복기**는
실제로 치른 면접 내용을 기록하면 AI가 종합 피드백을 생성해줍니다. 네 기능
모두 사용자가 쌓아온 이전 기록을 코사인 유사도 기반으로 검색해 답변에 참고
자료로 섞어 넣는 **RAG 그라운딩**을 갖추고 있고, 학습챗/면접복기 생성은 토큰
단위로 실시간 전송하는 **WebSocket 스트리밍**도 지원합니다(REST와 병행).

인증은 Bearer 토큰(JWT access + 회전형 refresh token) 방식이며, 로그인 UI
없이도 쓸 수 있도록 **게스트 계정**(`POST /auth/guest`)을 지원하고 나중에
데이터를 유지한 채 이메일/비밀번호로 전환할 수 있습니다. 그 외 세션(로그인
기기) 관리, 데이터 export, Ollama 모델 목록 조회, 헬스체크/Prometheus 메트릭
같은 부가 기능도 있습니다. LLM 호출은 전부 로컬 Ollama 엔진에 의존합니다.

## 주요 개선 및 버그 수정

209라운드 동안 나온 변경은 크게 아홉 갈래로 묶입니다. 초반 라운드는 새 기능
추가(RAG 확장, 페이지네이션, 세션 관리 API 등)와 테스트 커버리지 공백 메우기
위주였고, 중반부터는 보안 감사·동시성 버그·설정 검증 공백을 훑는 라운드가
이어졌으며, 후반부는 WebSocket 예외 처리와 RAG/AI 호출 견고성을 파고드는
"같은 버그 계열을 끝까지 쫓는" 라운드들이 많았습니다(예: WS의
`receive_json()` 예외 처리는 JSONDecodeError → KeyError → RecursionError →
ValueError까지 네 라운드에 걸쳐 형제 예외 타입을 하나씩 잡아나갔습니다).

### 인증/보안

- 게스트 계정(`POST /auth/guest`) 도입과, 데이터를 유지한 채 실계정으로
  전환하는 승격 API 추가 (#2)
- Refresh token 재사용 탐지 — 이미 폐기된 토큰이 재사용되면 탈취 의심으로
  보고 그 사용자의 전체 세션을 강제 로그아웃 (#19), 로테이션 자체의
  check-then-act 경쟁도 CAS로 마저 방어 (#83)
- 로그인 세션(활성 기기) 목록 조회/개별·전체 강제 로그아웃 API (#30)
- `JWT_SECRET_KEY` 최소 길이·`JWT_ALGORITHM` 허용 목록 검증으로 취약한 값이
  기동 자체를 막도록 함 (#55, 라운드200)
- 로그인 타이밍 공격(존재하지 않는 이메일과 틀린 비밀번호의 응답 시간 차이로
  계정 존재 여부 유출) 방지 — 항상 bcrypt 비교를 수행하도록 통일 (#58)
- HSTS 헤더, `Cache-Control: no-store` 전체 응답 적용 (#57, 라운드109)
- 이메일 대소문자 정규화로 중복 계정 생성 방지 (#63), 422 검증 오류 응답에서
  비밀번호 등 민감 값이 평문 노출되던 문제 수정 (#64)
- `X-Forwarded-For` 신뢰 설정(`--proxy-headers`) 누락으로 IP 기준 레이트리밋이
  사실상 무력화돼 있던 인프라 버그 수정 (#59)
- 비밀번호 변경/게스트 승격 시 기존 refresh token 전체 폐기 — 탈취된 토큰이
  비밀번호 변경 후에도 계속 유효하던 문제 (#107, 라운드207)
- 활성 refresh token이 하나도 남지 않아 재접근이 불가능해진 게스트 계정을
  매일 정리하는 스케줄러 job 추가 (라운드159)
- WebSocket 인증 토큰이 uvicorn 기본 로그에 평문으로 찍히던 문제(`--log-level
  warning`으로 해소, 라운드175), 오래 열린 WS 연결이 access token 만료 후에도
  계속 유효하던 문제(메시지마다 만료 재확인, 라운드190)
- 레이트리밋 한도를 소모한 실패 응답(401/404/409 등)에도 `X-RateLimit-*`
  헤더가 누락되던 문제 (라운드178)

### 동시성/경쟁 상태

- 회원가입/이메일 변경 동시 요청이 처리되지 않은 `IntegrityError`(500)로
  끝나던 문제 — DB unique 제약 위반을 잡아 깔끔한 409로 변환 (#77)
- 면접연습 답변 동시 제출 시 답변이 조용히 사라지고 중복 턴이 생기던 lost
  update 버그 — `WHERE answer IS NULL` compare-and-swap으로 해결 (#78)
- 퀴즈 재제출/면접복기 수정/면접연습 진행 등 여러 곳의 check-then-act 경쟁을
  `SELECT ... FOR UPDATE` 잠금으로 직렬화 (#92, #101, #102, 이후 두 라운드에
  걸쳐 잠금 도입 자체가 만든 회귀도 추가로 수정 #103, #104)
- 세션/퀴즈/면접 리소스가 요청 처리 도중(느린 AI 호출 사이) 삭제되면
  `IntegrityError`가 그대로 새어나가던 문제를 학습챗/퀴즈/면접연습/면접복기
  전 생성 경로에 걸쳐 전수 수정 (#105, #106, 라운드144~147, 165)
- 계정 자체가 요청 도중 삭제되는 경쟁(다른 탭에서 동시 탈퇴)도 로그인/토큰
  갱신/각종 생성 API 전반에 걸쳐 401로 안전하게 처리하도록 정리
  (라운드145~147)
- 리소스 UPDATE(이름 변경, 세션 폐기 등) 도중 그 리소스가 사라지면 나던
  `StaleDataError`(500)를 계정/세션/refresh token 등 잠금 없는 UPDATE
  경로 전반에서 404/401로 변환 (라운드160~162, 174, 197)

### WebSocket 견고성

- 학습챗 응답 스트리밍 WebSocket 도입 (#11), 이후 레이트리밋(#27)·유휴
  타임아웃(#87)·메시지 크기 제한(#80)·동시 연결 수 상한(라운드99) 등
  운영에 필요한 안전장치를 순차적으로 추가
- **`receive_json()` 예외 처리 시리즈**: 깨진 JSON 프레임(`JSONDecodeError`,
  #100) → 바이너리 프레임(`KeyError`, 라운드203) → 깊게 중첩된 JSON
  (`RecursionError`, 라운드204) → 거대 숫자 리터럴(`ValueError`, 라운드205)
  순으로, 같은 호출부가 낼 수 있는 형제 예외 타입을 한 라운드씩 찾아 전부
  `{"type": "error"}` 프레임으로 우아하게 처리하도록 메웠습니다
- 예상 못 한 서버 예외(WS 스코프는 전역 예외 핸들러가 적용 안 됨)를 잡아
  에러 프레임 + 로깅 후 연결 종료하도록 보강 (#163, 라운드139)
- 서버 재배포(SIGTERM, close code 1012)로 끊긴 연결을 "클라이언트가 끊음"으로
  잘못 로깅하던 문제, 클라이언트가 먼저 사라진 뒤 에러 프레임 재전송을
  시도하다 `RuntimeError`가 새던 문제 수정 (라운드185, 186)
- 동시 WS 연결 수에 상한이 없어 활성 연결만으로 DB 커넥션 풀이 고갈될 수
  있던 문제 — 상한 설정 + 초과 시 accept 전 거부 (라운드99)
- WS 연결/해제를 구조화된 접근 로그·Prometheus 지표에 남기지 않던 공백을
  메움 (라운드169, 173)

### RAG/AI 호출 견고성

- 면접연습에도 RAG 그라운딩 확장 (#1), RAG 색인 실패 로깅 추가 (#4)
- Ollama가 200과 함께 JSON이 아닌 본문을 주는 경우를 `OllamaServiceError`로
  통일 (#76), 빈/공백 응답을 예외 없이 그대로 반환하는 문제를 퀴즈 생성부터
  시작해(#8) 면접연습 첫 질문/피드백(#150, 라운드148~149), 학습챗/면접복기
  스트리밍(라운드188), 범용 Ollama 프록시 엔드포인트(`POST /chat`,
  라운드208)까지 모든 호출부에 재시도(최대 2회) + 공백 검증으로 메움
- `chat_stream()`이 스트리밍 도중 Ollama가 실패해도 예외 없이 조용히 끝나
  partial(심지어 빈) 응답을 정상 완료로 착각해 커밋하던 문제 (라운드187)
- RAG 검색이 사용자의 색인된 기록 전체를 이벤트 루프에서 그대로 채점해
  기록이 쌓일수록 다른 사용자 요청까지 함께 멈추던 문제 — 스레드로 위임
  (#114), bcrypt 해싱도 같은 이유로 스레드로 이동 (#115)
- 리소스 삭제와 RAG 재색인이 경쟁하면 고아 색인이 영구히 남아 지운 내용이
  다른 질문의 그라운딩 자료로 되살아나던 문제 — 요청 경로는 그대로 두고
  일일 백필 job에 "원본 없는 색인 정리" 스윕 추가 (라운드179)
- RAG가 자기 자신의 DB 조회/커밋 실패를 삼키지 못해 본 기능(채팅)까지
  크래시시키던 문제, `session.rollback()`이 무관한 다른 로드 객체까지
  expire시켜 `MissingGreenlet`을 유발하던 문제를 SAVEPOINT 기반으로 정교하게
  해결 (라운드198, 199)
- RAG 조회 이후 AI 호출 내내 DB 커넥션을 붙들고 있어 동시 사용자 몇 명만
  써도 커넥션 풀이 고갈되던 문제 — 학습챗/퀴즈/면접연습 생성 경로 전반에
  조기 커밋 적용 (라운드193~196)
- 차원이 다른 임베딩 벡터가 조용히 완벽한 점수(1.0)를 받아 검색 1등을
  차지하던 문제(라운드192), 원소 타입이 숫자가 아닌 오염된 임베딩 청크
  하나가 그 사용자의 RAG 전체를 사실상 영구 무력화하던 문제(#233,
  라운드209)

- 학습챗이 매 메시지마다 세션 전체 히스토리를 프롬프트에 다시 실어 보내던

### DB/마이그레이션

- 페이지네이션·정렬 쿼리의 동률(tie) 처리 — 타임스탬프만으로 정렬하면 같은
  값을 가진 행 사이 순서가 SQL 표준상 정의되지 않아 페이지 간 중복/누락이
  생길 수 있던 문제를 `id`(또는 마이크로초 정밀도 파이썬 클럭)를 2차 정렬
  기준으로 추가해 여러 라운드에 걸쳐 전수 정리 (#94, 라운드100, 103,
  116~118, 124, 127, 131, 155, 157, 177, 201)
- `CREATE INDEX CONCURRENTLY`로 배포 중 테이블 락을 피하도록 마이그레이션
  수정 (라운드115, 171), 빌드가 중단되면 재배포가 영구히 막히던 문제까지
  자동 복구되도록 보강 (라운드180)
- 데이터 손실 위험이 있는 downgrade(게스트 계정 nullable 컬럼 되돌리기 등)가
  안내 없이 로우레벨 예외로 죽던 문제 — 명확한 에러로 먼저 막도록 수정
  (라운드184)
- Postgres 세션 timezone GUC가 UTC가 아니면 `func.now()`와 파이썬
  `utcnow_naive()`가 서로 다른 값을 만들어 정렬이 어긋나던 문제 — 연결 시
  timezone을 명시적으로 UTC 고정 (라운드202), 같은 컬럼을 호출부에 따라
  DB 클럭과 파이썬 클럭으로 섞어 쓰던 문제도 정리 (라운드206)
- `DATABASE_URL`에 `sslmode=` 파라미터가 붙으면(관리형 Postgres에서 흔함)
  모든 요청이 `TypeError`로 실패하던 문제 (라운드205)

### 설정/검증

- 서비스 설정값(`JWT_SECRET_KEY`, `LOG_LEVEL`, `ENVIRONMENT`, 각종
  레이트리밋 문자열, 프롬프트 길이, 토큰 만료 시간, 퀴즈 문항/보기 수 상한,
  본문 크기 상한, WS 동시 연결 수/유휴 타임아웃, RAG 관련 수치 등)에
  `field_validator`를 하나씩 추가해, 오타나 극단값을 넣어도 앱은 멀쩡히
  뜨면서 특정 기능만 시작 시점엔 전혀 티 안 나게 계속 실패하던 클래스의
  버그를 광범위하게 막았습니다(라운드31~50대에 걸쳐 반복적으로 발견·수정)
- 공백-only 입력(제목/본문/답변 등)이 검증을 통과해 빈 항목처럼 보이는
  리소스가 만들어지던 문제 — `NonBlankStr` 공용 검증자 도입 후, zero-width
  space 등 화면엔 안 보이는 유니코드 서식 문자(라운드163)와 한글 채움 문자
  (라운드201)로 우회 가능하던 구멍까지 마저 막음
- 프로덕션에서 `ENVIRONMENT` 오타 시 Swagger/ReDoc이 계속 공개로 열려
  있던 fail-open 문제 (#74), `docker-compose.yml`이 그 값을 컨테이너에
  아예 전달하지 않아 `.env`를 정확히 채워도 무력화되던 인프라 버전의 같은
  버그(라운드113)
- `OLLAMA_BASE_URL`/`CORS_ORIGINS`의 트레일링 슬래시로 Ollama 호출/CORS가
  조용히 깨지던 문제 — 거부 대신 정규화로 해결 (라운드182, 183)
